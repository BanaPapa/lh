## 1. 이 앱이 하는 일

LH 신축매입약정 서류심사 중 **좌표로 자동 판정할 수 있는 두 항목**을 계산한다.

| 단계 | 심사표상 위치 | 이 앱의 역할 |
|---|---|---|
| **1차** | 심사표 2항 「매입제외(불가) 사유」 15개 항목 중 「주거환경 저해시설」 | 사업지 대지경계에서 유해시설 경계까지 거리를 재고, 신청유형별 임계거리와 대조해 적격/부적격 판정 |
| **2차** | 심사표 3항 「매입여건 평가점수」 중 생활편의성 40점 | 대중교통·주거여건·교육여건 등급을 심사표 등급표로 산정 |

### 1.1 이 앱의 위치 — 교차검증 도구

LH는 외부망을 쓸 수 없어 **납품본은 정적 데이터셋 방식**(진용성 대표 프론트 + 박진주 대표 표준 데이터셋 + 정민재 이사 룰북)이다.
이 앱은 **실시간 공개 API로 같은 판정을 독립 수행해 그 데이터셋의 오류를 잡아내는 검증 경로**다.

```
납품본  : 프론트 + delivery.zip(정적) + 룰북 v1.4      → LH 내부망 실행
검증본 A: 조준환 국장 엔진 + delivery.zip(정적)        → 같은 데이터, 다른 계산기
검증본 B: 이 앱 + 공개 API(실시간)                     → 독립 원천  ★
```

세 구현이 UI·구현방식은 달라도 **LH 기준조건은 동일하게 만족해야** 대조가 성립한다.

### 1.2 이 앱이 하지 않는 것

- 심사표 총점 100점 판정. 생활편의성 40점 외 60점(공가율·세대수 증가율·재무영향도·접면도로·주차대수·정책사업)은 공간분석 대상이 아니다. **합격선 70점 판정을 이 화면에서 내리지 않는다.**
- 매입제외 15개 항목 중 나머지 14개. 전 항목을 화면에 싣되 「별도 확인」으로 표시한다.

## 2. 실행 방법

### 2.1 백엔드

```powershell
cd backend
.\.venv\Scripts\Activate.ps1
uvicorn app.main:app --reload --port 8000
```

### 2.2 프런트엔드

```powershell
cd frontend
npm run dev          # http://localhost/ (vite.config 에서 포트 80)
```

1. 상단 검색창에 사업지 주소 입력 → 검색

### 4.2.1 2026-09-11 LH 확정 — 정문 3단 · 문 후보 · 다필지 · 최단거리선 (API 검증판)

2차 보고 회의 결정을 백엔드에 반영했다(상세 근거는 `docs/hazards/MEASUREMENT.md §3`).

- **정문 3단 확장 (#8)** — 종합병원(`hospital` 시설군)도 대학과 같은 3단으로 잰다:
  수기 지정 정문 필지/좌표 → 네이버 「{시설명} 정문」 → 좌표 폴백+고지. 측정은
  `AmenityCollector._measure_with_front_door()` 하나로 일원화했다(대학·종합병원 공용).
  좌표 폴백 고지는 결정 근거를 드러낸다(「정문 미확인 — 시설 좌표 기준(LH 확정
  2026-09-11: 대형 필지 시설은 정문 기본)」). 시설·시설군 헤더 모두에 고지가 실린다.
  네이버 지역검색 호출은 시설당 1회(반경 내 대학·종합병원 수만큼만 증가).
- **문·출구 후보 (#7·#11)** — `ScreeningFacilityHit.front_door_candidates:
  list[FrontDoorCandidate{label, coordinates, distance_m, selected}]`. 정문·후문·동문·
  서문·남문·북문·출입구·「N번 출구」류를 전부 후보로 모으고, 기본 `selected` 는 사업지
  최근접 문(수기 지정이 있으면 그것). 후보가 1개뿐이면 그 1개만. 철도·지하철역도 같은
  필드로 출구 후보를 싣는다.
- **다필지 합집합 자동 해석 (#9)** — `/parcels/resolve`(ParcelResolver)가 주소의 복수
  지번을 모두 해석해 `parcels` 에 담는다(첫 항목 = 대표). 파서
  `app/hazard_review/multi_parcel.parse_multi_parcel_address()` 는 순수 함수이며
  `46-2, -45` · `410-3, 411, 412-44, -45, 413-2` · `1243, 1244` ·
  `734-16 외 4필지(11,13,15,25)` · `산8-15` 표기를 지원한다. 인접 지번은 로컬 지적도
  (법정동코드 조립 → `parcel_by_pnu`) 우선, 없으면 VWorld/카카오로 푼다. 「외 N필지」
  목록이 없으면 대표만 해석하고 `note` 에 담당자 추가 선택을 요구한다. 합집합 경계는
  기존 `_site_boundaries`·`_site_rings`(전 필지)·`max_extent_multi` 가 그대로 쓴다.
- **사업지↔시설 최단거리선 (#5)** — `ScreeningFacilityHit` 에 1차 `HazardFacility` 와
  같은 형태의 두 좌표를 싣는다: `nearest_boundary_point`(사업지 대지경계 위 최단점,
  경계 없으면 null → 주소점) · `nearest_facility_point`(거리를 만든 시설 측 기준점).
  프런트는 1차와 같은 그리기 코드를 재사용한다.

### 4.2.2 2026-09-11 LH 확정 #5 — 석유대체연료 판매업 용도지역(지적편집도)

석유대체연료 판매업은 25m(RB14-FUEL25)를 적용하되, 사업자등록 소재지만 있는 경우
(주거지역 빌라·사무실 등)를 가려내기 위해 **용도지역을 함께 표시**한다. 정민재 액션
「API 검증판 용도지역 레이어 추가」가 이 구현이다.

- **조회** — `VWorldClient.zoning_at(lat, lng)` 가 VWorld 2D 데이터 API 용도지역 레이어
  `LT_C_UQ111` 을 시설 좌표로 점 조회한다(`geomFilter=POINT(lng lat)`, `crs=EPSG:4326`).
  응답 속성 키는 `uname`(실측 예: 정읍 수성동 1011-8 → 「제2종일반주거지역」, 익산 영등동
  191-35 → 「일반공업지역」). 한 점에 용도지역 폴리곤이 겹쳐 오면 첫 비공란 `uname` 을
  쓴다. 미확인이면 20m 반경 `BOX` 로 1회 재조회한다. 실패·미확인·키 없음은 `None`
  (예외로 죽지 않는다). 좌표 6자리 반올림 키로 프로세스 메모리에 캐시해 배치에서 같은
  시설을 반복 조회하지 않는다.
- **분류** — `classify_zoning(name)` 순수 함수: 「주거」 포함(전용·일반·준주거) →
  `residential`, 공업·상업·녹지·관리 등 → `non_residential`, 공란·`None` → `unknown`.
- **부착 범위** — `HazardReviewService._attach_zoning()` 이 **RB14-FUEL25 의 판정창 이내
  석유대체연료 후보(`metadata.dataset == "petroleum_alt_fuel_retailers"`)에만** 붙인다.
  주유소·CNG·LPG 충전소는 조회하지 않는다(결정 범위 밖, VWorld 호출 절약).
- **상태 규칙** (`_decide_status` 의 일반 applied 경로 · `_petroleum_zoning_hold`):
  석유대체연료 후보가 임계 25m 이내라도 `zoning_class` 가 `residential`·`unknown`(미조회
  포함)이면 **`exclusion_match` 로 올리지 않고 `review_required`** 로 남긴다(근거 문장
  「확인 요청 — 용도지역 {명칭} 소재 … 사업자등록 소재지 가능성, 담당자 판단」).
  `non_residential` 로 확인되면 기존대로 25m 확정하고 근거 문장에 「용도지역 {명칭}」을
  병기한다. 여유구간(검토) 구간 처리는 기존과 같다.
- **프런트** — `HazardFacility.zoning_name`/`zoning_class`/`zoning_source` 를 1차 근거 행과
  지도 마커 이름표에 표시하고, 주거·미확인이면 「확인 요청」 배지를 단다. 지도에는 카카오
  지적편집도 오버레이(`MapTypeId.USE_DISTRICT`) 토글 버튼을 줌 컨트롤 옆에 두며, 확인
  요청 결과가 뜨면 자동으로 켠다(사용자가 끄면 그 세션 동안 다시 켜지 않는다). 네이버
  모드·키 없음이면 버튼을 비활성한다.

### 4.3 판정 상태값 (룰북 §11)

| 상태 | 의미 |
|---|---|
| `exclusion_match` | 적용 Rule·데이터·경계가 충족되고 임계거리 이내 |
| `no_conflict_in_snapshot` | 사용 데이터 범위에서 충돌 미발견. **매입 적격을 뜻하지 않음** |
| `review_required` | 후보는 있으나 조건·매칭·예외·경계 중 하나가 미확정 |
| `dataset_missing` | 필요 데이터셋 미확보 |
| `geometry_missing` | 사업지 또는 시설 경계 미확보 |
| `not_applicable` | 해당 유형에는 Rule 미적용 |

### 5.3 미확보 시설군 처리 — 범위 산정

원천이 없는 시설군을 "0건"으로 두면 **없는 것이 확인된 것처럼** 읽힌다.
미확보 시설군을 **최악(없음)·최선(있음)** 두 번 평가해서,

- 두 값이 같으면 → 점수 확정
- 다르면 → **"산정 가능 범위 9~15점"** 으로 표시하고 무엇이 미확보인지 명시

상위 등급이 이미 성립하면 미확보가 있어도 확정된다. (예: 0.5km 내 교통시설 2개가 이미 있으면 환승시설 미확보와 무관하게 만점 확정)

### 5.4 산정 대상이 아닌 항목 (6종 · 60점)

공가율 20 · 주민등록세대수 증가율 10 · 지원단가 대비 탁감가액 비율 15 · 접면도로 넓이 10 · 주차대수 5 · 정책사업 5.

## 6. 통과 처리 정책

**원천이 없어 판정하지 못한 항목을 부적격으로 몰지 않는다.** 대신 통과 처리하고, 왜 통과 처리했는지 항목마다 한국어로 남긴다.

| 판정 상태 | 심사 결과 | 표시 |
|---|---|---|
| `exclusion_match` | **부적격** | `매입제외` + 사유 |
| `review_required` | 검토 필요 | `검토 필요` + 사유 |
| `no_conflict_in_snapshot` | 통과 | `통과` |
| `dataset_missing` | **통과** | `통과` + `판정 미적용·통과 처리` + 사유 |
| `geometry_missing` | **통과** | 위와 동일 |
| `not_applicable` | 해당 없음 | `해당 없음` + 미적용 사유 |
| 판정 제외 (군부대·사격장) | **통과** | 협의에 따른 판정 제외 |
| 수기 확인 대상 | **통과** | 별도 수기 확인 |
