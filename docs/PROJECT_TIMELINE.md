### 1.1 산출물 3갈래

LH 는 외부망을 쓸 수 없다. 그래서 납품본은 정적 데이터셋 방식이고, API 방식은 검증 도구다.

```
납품본   진용성 프론트 + 박진주 표준 데이터셋 + 정민재 룰북   → LH 내부망 실행
검증본 A 조준환 국장 Python 엔진 + 박진주 데이터셋           → 같은 데이터, 다른 계산기
검증본 B 이 저장소 + 공개 API 실시간                        → 독립 원천
```

세 구현이 UI·구현방식은 달라도 **LH 기준조건은 동일하게 만족해야** 대조가 성립한다.

### 3.3 공장 판정 완화 (8-25)

> 공장의 경우 — 인접하는 사례는 매우 적을 것으로 보이며, 이게 대기오염물질 배출공장인지
> 아닌지를 알 수 있는 방법이 마땅치 않아서, ⇒ **공장 인접 여부만 판정하고 '정밀조사 요구'
> 라는 메시지만 남겨도 충분**할 듯 합니다.

→ 판정은 공장을 `exclusion_match` 로 올리지 않는다. LH 8-29 구두 지시로 이 원칙이
나·다목까지 확대됐다(§3.6 · 룰북 §6.1).

> **주의 (8-30 정정).** 종전 이 자리에는 *"현재 코드는 `factory_registry` 미적재로 공장
> 4항목이 `dataset_missing` 이며, 심사 계층에서 통과 처리 + 사유 표시로 내려간다.
> LH 회신 취지와 부합한다"* 고 적혀 있었다. **이 서술이 사고를 가렸다.**
> 「원천 미적재라 통과 처리」와 「인접 공장이 없어 통과」는 결과가 같아 보이지만 전혀 다르다.
> 전자를 LH 회신 취지와 부합한다고 적어 두면 원천이 안 붙은 상태가 정상으로 읽힌다.
> 경위와 조치는 §6 에 있다.

### 6.2 왜 안 보였나 — 이게 진짜 교훈이다

빠진 원천의 시설군은 `dataset_missing` 이 되는데, `app/screening/service.py` 의 결과 매핑이
이것을 `outcome="pass"`(passthrough)로 접는다.

```python
if status == "dataset_missing":
    return "advisory", "pass", True, "판정 미적용 — 통과 처리"
```

그래서 스냅샷의 `categories` 만 보면 공장 5종이 118건 전부 `pass` 로 보인다.
**「근처에 공장 없음」과 「공장 데이터가 아예 없음」이 출력에서 구분되지 않았다.**
로컬 원천 적재를 직접 돌려 `factory_registry_loaded=False` · `factory_pnus=0` 을 확인하고서야
드러났다.

> 커밋 f730428 「조회하지 않은 원천을 「충돌 없음」으로 만들지 않는다」가 판정 **안에서** 세운
> 원칙을, 산출물 층에서는 세우지 않았던 것이다. 같은 원칙을 한 층 위에서 다시 세운다 —
> 스냅샷은 `outcome` 과 별도로 상태값 6종을 그대로 싣고, 미배선 시설군이 있으면 판정을
> 시작하지 않는다.

### 6.3 측정 기준까지 흔들렸다

`cadastral` 이 없으면 시설 쪽 경계 폴백이 없다. 사업지는 `geometry_source=parcel_polygon` 으로
118건 전부 정상이었으나, 시설은 점으로 남아 측정이 아래쪽으로 떨어진다.

```
PARCEL_MEASUREMENT   = "대지경계 ↔ 대지경계 최단거리"          # LH 공고 기준
BOUNDARY_MEASUREMENT = "신청 대지경계 ↔ 시설 후보점 최단거리"   # 실제보다 멀게 나온다
```

조준환 국장님이 축1에서 LH 기존 웹앱을 비판한 근거 — 「중심점 방식은 구조적으로 느슨하게
판정된다, 임계 반전 10건 전건이 미탐 방향」 — 이 우리 대조 도구에 그대로 해당됐다.

### 6.4 파생 사고 2건 (같은 날 · 먼저 발견돼 먼저 고침)

| # | 증상 | 원인 | 조치 |
| --- | --- | --- | --- |
| 1 | 118건 중 114건이 「검토 필요」로 나옴 | **원천 캐시 스탬피드.** 캐시 확인과 채우기 사이에 잠금이 없어 동시 판정 3건이 각자 전국 목록을 긁고 data.go.kr 이 스로틀 | `app/services/single_flight.py` 의 `LoopSafeLock` 도입(double-checked · 실패는 캐시하지 않음). kgs·safemap·crematorium·noise_emission 적용 |
| 2 | 같은 조건 두 런이 42건 갈림 | **오피넷은 사업지별 반경 조회**라 118건이면 118회 호출된다. 전국 목록 예열 대상에서 빠져 있었고 40여 건부터 스로틀 | 커버 지점 집합을 한 번 조회해 스냅샷을 데우고 거리로 거르는 방식으로 전환 |

두 사고 모두 f730428 덕분에 드러났다. 그 커밋 이전이었다면 실패한 원천이 조용히 「충돌 없음」으로
둔갑해 **아무 일도 없는 것처럼 보였을** 것이다.

### 6.5 폐기한 산출물

미배선 상태에서 나온 것이라 전부 무효다. 인용 금지.

- 8-30 산출 스냅샷 4종(general·multi_child × 여유구간 100·150)과 그 `baseline_pre_*` 사본
- `data/ours_118d.json` (8-27 산출 · 저장소에 커밋돼 있음) — **조준환 국장님이 파일로 요청한 바로 그것**
- 그 스냅샷들로 낸 여유구간 실영향 수치

> **전달 보류.** 재산출 전까지 118건 결과 파일을 팀에 보내지 않는다. 지금 보내면 조준환 국장님이
> 「내 28 ↔ 그의 18」 원인 분해에 시간을 쓰고 결론이 「대조 도구에 원천이 안 붙어 있었다」로
> 끝난다. 우리가 먼저 말하는 편이 낫다.

### 6.6 재발 방지

1. 대조 도구와 앱이 **같은 조립 경로**로 서비스를 만든다. 진입점이 갈라지면 또 벌어진다.
2. 스냅샷은 상태값 6종을 그대로 싣는다. `dataset_missing` 이 `pass` 로 접혀 보이지 않는다.
3. 판정 시작 전 시설군별 배선 상태를 출력하고, 미배선이 있으면 **판정을 시작하지 않는다**
   (`--allow-degraded` 로만 강행 · meta 에 미배선 목록 기록).
4. 같은 조건 두 런이 동일한지를 스냅샷 산출의 **합격 기준**으로 둔다.

> 룰북 §3 재현성 조항(「동일 입력·Rule 버전·데이터 스냅샷·Geometry 면 동일 결과」)은 원래
> 판정 규칙에 건 조건이었으나, 실시간 API 구조에서는 산출 절차에도 걸어야 성립한다.
> 조준환 국장님이 LOCUS 를 「오프라인 번들 — 판정에 외부 통신 없음」으로 만든 이유가
> 구조 취향이 아니라 재현성이었음을 우리 손으로 실증한 셈이다.
